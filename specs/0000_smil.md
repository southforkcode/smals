# Small Machine Intermediate Language

- Specify the typed intermediate representation shared by SMAls compilers and backends.
- Preserve logical values, explicit control flow, storage validity, and defined terminal outcomes across targets.
- Define the scope and conformance rules for the accompanying specifications.

## Requirements

| KEY | Requirement |
| --- | --- |
| SMIL-001 | SMIL shall represent computations as typed, immutable SSA values and storage changes as explicit operations. |
| SMIL-002 | Each function shall use a flat CFG of basic blocks with explicit successor edges and ordered block arguments. |
| SMIL-003 | Logical operation semantics shall be independent of native register widths, instruction selection, physical frames, and target storage encoding. |
| SMIL-004 | A conforming tool shall distinguish source parsing, semantic verification, target binding, machine linking/loading, and runtime execution. Success at one boundary shall not imply success at the next. |
| SMIL-005 | A required static rejection shall produce a diagnostic and shall prevent publication of the invalid artifact. An unsupported target requirement shall be diagnosed rather than approximated by weaker semantics. |
| SMIL-006 | A reached terminal fault shall produce no normal result, preserve earlier completed observable effects, prevent further normal SMIL commits, and terminate the program instance without implicit unwinding or orderly shutdown. |
| SMIL-007 | The core shall not assign undefined behavior, `undef`, `poison`, or arbitrary result values to the invalid execution conditions specified by this specification set. |
| SMIL-008 | An ordinary executable operation with constant faulting operands shall remain well-formed when it satisfies static rules; it shall fault only if executed. A required constant expression shall instead be rejected if it cannot evaluate successfully. |
| SMIL-009 | Native instructions, expanded sequences, constant folding, and runtime helpers shall obey the same logical operation definitions, including result widths, flags, checks, and fault conditions. |
| SMIL-010 | Claims of source, object, runtime, or backend conformance shall identify the applicable versioned contracts and satisfy the relevant conformance cases in this set. Profile definition alone shall not establish backend availability. |
| SMIL-011 | The core shall accept only the operations and forms defined by these specifications. Arrays, unions, packed/vector/floating-point types, generic volatile RAM, weak atomics, raw continuations, dynamic allocation, dynamic module loading, and uncontracted foreign transfers require separately specified extensions. |
| SMIL-012 | A guide example containing placeholders or omitting enclosing declarations shall not be treated as an independently publishable source module. Intentionally invalid examples shall retain their specified rejection or fault behavior. |
| SMIL-013 | Version identifiers shall retain their distinct meanings: `smil.source.v1` for text; `smil.execution.checked.v1` for portable checked execution; `.checked.v2` for the reference profiles; and the individual transport identifiers specified in the module/linking documents. |
| SMIL-014 | A tool shall report an inability to process an input within its own memory or recursion limits rather than silently truncate a type width, alter tokens, or change source meaning. |

## Normative interpretation

“Shall” states a requirement; “may” permits a choice subject to all other requirements. Requirement keys are stable references for verification and later planning. Tables, equations, and the grammar explicitly incorporated by a requirement are normative. Conformance examples specify required observations, not a test implementation or an implementation sequence.

These documents specify required results and externally relevant contracts. They do not prescribe work order, milestones, staffing, or task decomposition. The guide's recommended implementation order, suggested initial CPUs, and optional internal algorithms are informative and are not converted into delivery requirements. Required deterministic algorithms, such as lifecycle ordering and canonical catalog assignment, remain contractual behavior.

The source grammar governs spelling and statement boundaries. Operation specifications govern logical semantics. The execution specification governs validation priority and fault commitment. A resolved target contract governs physical representation without changing those logical rules. A conflict between these authorities requires correcting the specification; it does not permit a tool to choose weaker behavior.
